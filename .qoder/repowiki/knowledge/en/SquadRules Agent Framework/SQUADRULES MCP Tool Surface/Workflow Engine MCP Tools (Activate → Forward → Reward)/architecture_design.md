Each file exposes a paired `executeX` pure function plus a `registerXTool(server, ...)` registration helper that mounts an MCP tool on the server. The three tools form a strict pipeline:
- `activate.ts` resolves search results into activation choices, canonicalizes adapter URIs, loads linked artifacts, and supports an authoring mode that routes through a built-in author-adapter; it emits `next_action` instructions guiding the agent to call `forward`.
- `forward.ts` drives a stateful multi-layer adapter execution: it starts/pins an execution in `forwardRuntimeStore`, validates authoring context consistency across calls, applies solutions against inference contracts or previous-step proofs, handles missing-proof redirection, tracks execution traces, and navigates layers via `resolveAdapterNextLayer`/`resolveAdapterPreviousLayer`.
- `reward.ts` finalizes an execution by evaluating the reward, persisting metrics via `applyRewardMetrics`, and recording structured trace data; it enforces a guard that a failed proof cannot be retroactively rated success.

Dependency direction is one-way: tools depend on services (`services/memory`, `services/qdrant`, `services/execution-trace-store`, `services/proof-of-work-store`, `services/reward-*`) but never on each other directly — cross-tool coordination happens through shared stores and URI contracts (`squadrules-uri`). Input/output schemas live in sibling `_schema.js` files and are validated via Zod's `safeParse` before business logic runs.
