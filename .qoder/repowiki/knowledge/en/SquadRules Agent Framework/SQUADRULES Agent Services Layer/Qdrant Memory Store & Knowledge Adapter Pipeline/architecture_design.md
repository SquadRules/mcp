The module is organized around a single public facade `MemoryQdrantStore` (store.ts) that owns a `QdrantClient`, resolves the collection alias via `resolveCollectionAlias`, and delegates to two internal collaborators:
- `MemoryQdrantStoreMethods` (store-methods.ts): read path — point retrieval, Redis-backed caching, hybrid vector+BM25+activation-pattern search using Qdrant's `query` API with RRF fusion and per-field boost weights.
- `MemoryQdrantStoreAdapter` (store-adapter.ts): write path — orchestrates header-based vs. default adapter storage, dispatching to `storeHeaderBasedAdapter` / `storeDefaultAdapter` after title-similarity de-duplication via `checkSimilarAdapterByTitle`.

Sub-files split responsibilities further: `adapter-builder.ts` parses Markdown into layered `Memory[]` objects (H1 sections → contract-block boundaries → layers, extracting activation patterns and reward signals); `qdrant-point-to-memory.ts` is the reverse deserializer; `store-init.ts` runs on startup to create/migrate collections (single-vector → named vectors, BM25 sparse config recreation, full-text payload indexes, activation-search backfill); `store-artifact.ts` handles non-Markdown attachments; `validate-protocol-structure.ts` and `validate-adapter-markdown-size.ts` enforce payload invariants; `activation-search-backfill.ts`, `activation-search-fields.ts`, `activation-pattern-payload.ts` manage activation-pattern vectors; `store-title-similarity-search.ts` performs title similarity checks; `memory-accessors.ts` exposes payload-version helpers.

Dependency direction is one-way outward: this module depends on `../embedding/service`, `../redis-cache`, `../code-block-processor`, and shared Qdrant utils (`../../utils/qdrant-utils.js`, `../../utils/qdrant-vector-types.js`), but nothing inside the module imports from HTTP/CLI/tool layers — it is a pure service boundary.
