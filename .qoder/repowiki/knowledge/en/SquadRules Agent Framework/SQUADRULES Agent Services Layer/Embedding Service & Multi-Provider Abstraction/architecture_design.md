The module is layered around a single `EmbeddingService` class (`service.ts`) that exposes `generateEmbedding`, `generateBatchEmbeddings`, `calculateCosineSimilarity`, `generateMemoryEmbedding`, `healthCheck`, and `getConfig`. Provider selection is split into two concerns: `provider-resolver.ts` computes the *candidate* provider from `EMBEDDING_PROVIDER` plus env vars (openai → tei → fastembed), while `providers.ts` dispatches to the concrete HTTP/local implementation via `postEmbeddings`, which also implements auto-fallback when an explicit candidate fails. Concrete backends live in `fastembed-provider.ts` (local ONNX model loaded lazily via dynamic `import('fastembed')`), and the OpenAI/TEI implementations are inline async functions in `providers.ts`. Cross-cutting concerns are isolated: `config.ts` resolves the embedding dimension and model name; `audit.ts` + `provider-audit.ts` emit structured audit events per call; `health.ts` runs a minimal probe; `lazy-probe.ts` memoizes the first dimension probe so eager boot and lazy CLI paths share one model load; `bm25-tokenizer.ts` provides BM25 tokenization used elsewhere; `types.ts` defines the public `EmbeddingResult` / `BatchEmbeddingResult` interfaces. Dependency direction is inward: service → providers → (fastembed-provider | config | provider-resolver | provider-audit); nothing inside the module imports from sibling services except shared metrics and tenant context.
