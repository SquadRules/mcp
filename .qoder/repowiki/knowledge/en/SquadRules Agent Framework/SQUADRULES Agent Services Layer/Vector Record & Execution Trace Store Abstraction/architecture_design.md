Two backend-agnostic ports define the module boundary: `IVectorRecordStore` (vector-bearing memory/adapter/artifact records) and `IExecutionTraceStore` (non-vector trace rows). Domain shapes live in `types.ts` and are explicitly forbidden from importing any backend client. The `lancedb/` subdirectory contains a single concrete implementation per port — `LanceVectorRecordStore` implements the record store by composing five internal layers (`LanceRecordEngine`, `LanceRecordReader`, `LanceRecordMutator`, `LanceRecordSearch`, `LanceRecordWriter`) over one shared `memory_records` table, while `LanceExecutionTraceStore` stores serialized `StoredExecutionTrace` JSON rows in an `execution_traces` table. Cross-cutting concerns sit at the module root: `lancedb-connection.ts` lazily imports `@lancedb/lancedb` and opens a strong-consistency connection (`readConsistencyInterval: 0`) to a per-user directory under `squadrules-config`; `commit-retry.ts` wraps all mutating operations in bounded exponential-backoff retry keyed on commit-conflict error messages; `embedded-store-singleton.ts` memoizes one `LanceVectorRecordStore` instance so both the DI-injected `memoryStore` and the legacy `qdrantService` singleton share it. Dependency direction is strictly inward: callers depend only on the two interfaces; backends are isolated under `lancedb/`. The record store also exposes a legacy `qdrantService` read/admin surface (e.g. `retrieveById`, `createOrUpdateAlias`, `getCollections`) as no-ops or delegations so existing callers can be migrated without breaking.
