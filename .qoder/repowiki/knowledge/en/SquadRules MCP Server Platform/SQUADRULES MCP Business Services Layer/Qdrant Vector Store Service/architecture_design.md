The module is organized as a thin facade over domain-scoped feature modules, all sharing one `QdrantConnection` instance:
- `connection.ts` — owns the `@qdrant/js-client-rest` client, TLS/CA setup, health checks, and exponential-backoff reconnection via `executeWithReconnect`, which is the single entry point for every DB call.
- `service.ts` — `QdrantService` class exposes a stable public API (store/retrieve/search/update/delete memory, protocol steps, resources, quality metrics, alias/collection management) and delegates to sub-modules; exports a singleton `qdrantService` that resolves at import time to either a real `QdrantService` or the shared embedded record store (`../vector-store/embedded-store-singleton`) cast to the same shape, selected by `isQdrantConfigured` from config.
- Feature modules: `memory-store.ts`, `memory-retrieval.ts`, `memory-updates.ts`, `search.ts`, `protocol.ts`, `listing.ts`, `quality.ts`, `resources.ts`, `reward-propagation.ts`, `initialization.ts`, `snapshots.ts` — each takes a `QdrantConnection` and performs one responsibility.
- Shared concerns: `types.ts` defines the upsert payload shapes (`UpsertResourceItem`, `UpsertResourceResult`); `utils.ts` provides `sanitizeAndUpsert`; `undici-compat.ts` bridges fetch quirks; `protocol.ts` / `quality.ts` / `reward-propagation.ts` encode the agent workflow's protocol-step and reward model in payload/index schema.
- Dependency direction is strictly inward: feature modules depend on `connection.ts` + shared utils; nothing inside this module imports sibling feature modules except `service.ts` wiring them together. External dependencies are `@qdrant/js-client-rest`, `../../config.js`, `../../utils/*`, `../redis-cache`, `../metrics/qdrant-metrics`, and `../id-generator`.
