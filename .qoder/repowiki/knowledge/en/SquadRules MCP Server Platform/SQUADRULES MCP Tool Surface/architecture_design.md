All child modules are MCP tool handlers that register themselves via `server.registerTool(...)` in their own files, but the authoritative contract is centralized in `tool-registry.ts`, which enumerates every tool name, title, description (resolved from embedded docs), strict input schema, output schema, and optional UI metadata. This registry is the single source of truth for MCP `tools/list`, the `/api/<tool>` HTTP routes, and CLI commands — ensuring cross-surface parity without importing Qdrant/OpenAI at import time. Cross-cutting concerns shared across children include: `forward-register.ts` + `forward-runtime` helpers (adapter URI resolution, input teaching, contract matching, error shaping, trace forwarding) used by both activate and forward; `artifact-catalog.ts` / `local-artifact-dir-contract.ts` / `train-mime.ts` for artifact path/MIME handling reused by export, train, and tune; `squadrules-uri.ts` and `next-pow-*` utilities consumed by forward/next step logic; and `reward.ts`'s review evidence validator reused by train/tune flows. The workflow enforced by the registry order is intent detection (activate) → layered execution (forward with proof-of-work steps) → outcome validation (reward).
