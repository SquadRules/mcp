Two MCP tool entry points with a shared activation→forward pipeline:
- `activate.ts` exposes `registerActivateTool`, which wraps `executeSearch`, maps search results into `ActivateOutput` choices (match/refine/create roles via discriminated union), resolves linked artifacts from the export catalog, and emits shell `materialize` commands targeting `$SQUADRULES_LOCAL_ARTIFACT_DIR`. Refinement sequences are tracked via `activateRefinementStore` keyed by an optional `execution_id`.
- `forward.ts` exposes `executeForward`, which loads the target layer via `loadMemoryForParsedUri`, starts/continues an execution in `forwardRuntimeStore`, dispatches on the adapter's inference contract (`tensor` vs. plain proof-of-work), applies solutions to prior layers via `next-previous-step`, validates against `expectedPreviousHash` using `proofOfWorkStore`, and advances to the next layer via `resolveAdapterNextLayer`.
- Schema definitions live in `activate_schema.ts` (Zod schemas + inferred TS types for input/output); `forward_schema.ts` is referenced but outside this scope.
- Dependency direction: both tools depend outward on `services/memory`, `services/qdrant`, `services/adapter-navigation`, `services/execution-trace-store`, `services/forward-runtime-store`, `services/proof-of-work-store`, and cross-tool helpers like `squadrules-uri`, `artifact-catalog`, `export-resolve-adapter`; they do not import each other directly — the orchestration is external.
- Observability: both registerers instrument `mcp-metrics` (calls, duration, errors, input/output size) and log via `structuredLogger`.
