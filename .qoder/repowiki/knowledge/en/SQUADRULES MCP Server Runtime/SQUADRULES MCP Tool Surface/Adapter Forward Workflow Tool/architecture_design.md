The module is organized as a thin MCP tool registration around a single stateful workflow engine:
- `forward-register.ts` exposes `registerForwardTool`, which registers the `forward` MCP tool with `inputSchema`/`outputSchema` from `forward_schema.ts`, wraps calls in metrics (`mcpToolCalls`, `mcpToolDuration`, `mcpToolErrors`, `mcpToolInputSize`, `mcpToolOutputSize`), and converts `SquadrulesError` into structured error responses via `forward-tool-error.ts`.
- `forward.ts` exports `executeForward`, the core orchestrator: parses the `squadrules://` URI, resolves the target memory (adapter slug → first layer, or direct layer UUID), starts or resumes an execution via `forwardRuntimeStore`, handles authoring-context pinning, elicits user input when required, delegates solution application to `next-previous-step.ts` / `next-pow-helpers.ts` for proof-of-work validation, updates step quality through `qdrantService`, appends traces, and builds the response view.
- `forward_schema.ts` centralizes all Zod schemas: `forwardInputSchema`, `forwardSolutionSchema` (with v1→v2 normalization via `normalizeForwardSolutionFormat`), `forwardContractSchema`, `forwardNextCallSchema` (discriminated union of `kind: 'forward' | 'reward'`), and the wire schema `forwardMcpWireInputSchema` used by the MCP transport. It also defines the `ForwardInput` / `ForwardOutput` TypeScript types.
- `forward-view.ts` renders the canonical `ForwardOutput`: `buildForwardView` composes `current_layer`, `contract` (from stored contract or generated challenge via `buildChallenge`), `next_call` (forward with pre-filled `solution_template` using `buildEmptySolutionTemplate`, or reward with outcome derived from `proofOfWorkStore.getResult`), UI summary fields, and local artifact dir hints; `mapLayerPayloadShapeToForwardView` adapts payloads returned from nested forward invocations.
- `forward-trace.ts` serializes solutions into `TensorValue` records and persists them via `executionTraceStore.appendTrace` in a fire-and-forget fashion.
- `forward-helpers.ts` provides shared evidence hint builders and template placeholders (`<real stdout>` / `<real stderr>`) used across the pipeline.

Dependency direction is one-way: register → executeForward → helpers/views/tracing → services (memory store, qdrant service, forward-runtime-store, proof-of-work-store, execution-trace-store). The module does not import sibling tools except for cross-cutting utilities (`next-pow-helpers`, `next-previous-step`, `next-missing-proof-payload`, `next.js` for `updateStepQuality`).
