Single-file entry point `src/tools/next.ts` exposes `_executeNext` (used by the forward bridge and legacy HTTP route) which orchestrates a fixed pipeline: normalize layer URI → load memory with Redis cache → optional user-input elicitation → pin layer manifest → attempt to apply solution to previous step when the current step has no contract → validate proof via `handleProofSubmission` → check previous-step completion → resolve next layer → build challenge payload. Internal helpers are split by concern: `next-pow-helpers.ts` holds nonce rotation, proof hashing (`sha256` of canonicalized record), per-type validation (shell/forward/user_input/comment/subagent), retry counting, and semantic comment similarity; `next-pow-challenge-shape.ts` renders the challenge object from stored `ProofOfWorkDefinition`, sanitizing untrusted subagent.mcp entries and unknown types into `SquadrulesError`; `next-previous-step.ts` implements two recovery paths — applying a submitted solution to the previous step when the current step lacks a contract, and detecting when a client forwarded the wrong URI; `next-missing-proof-payload.ts` builds the MISSING_PROOF response carrying the previous step's challenge with correct nonce/proof_hash; `next_schema.ts` defines Zod schemas for `nextInputSchema` / `nextOutputSchema` / `solutionSchema` / `challengeSchema` that form the wire contract between agent and server. Dependency direction is one-way: schema/types ← helpers ← orchestration, with all persistence going through `services/proof-of-work-store`, `services/memory/*`, `services/qdrant/service`, and `services/redis-cache` rather than direct DB access.
