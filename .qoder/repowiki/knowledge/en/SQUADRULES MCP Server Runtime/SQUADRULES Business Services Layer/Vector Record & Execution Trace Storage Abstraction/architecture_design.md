Two orthogonal ports define the module boundary: `IVectorRecordStore` (vector-bearing memories, adapters, artifacts) and `IExecutionTraceStore` (non-vector trace rows), both typed against shared domain shapes in `types.ts` (`Memory`, `LayerRecord`, `StoredExecutionTrace`, `TrainingPair`). The only concrete backend lives under `lancedb/`: `LanceVectorRecordStore` implements `IVectorRecordStore` by delegating to five focused sub-classes — `LanceRecordEngine` (connection + table lifecycle + MVCC upserts via `mergeInsert`), `LanceRecordReader`, `LanceRecordMutator`, `LanceRecordSearch`, and `LanceRecordWriter`. `LanceExecutionTraceStore` is a separate class implementing `IExecutionTraceStore`, storing each execution as one JSON row in an `execution_traces` table. Cross-cutting concerns live at the module root: `lancedb-connection.ts` lazily imports `@lancedb/lancedb` and opens a strong-consistency connection (`readConsistencyInterval: 0`) to a per-user directory; `commit-retry.ts` wraps every write with exponential-backoff retry keyed on conflict-error regexes; `embedded-store-singleton.ts` memoizes a single `LanceVectorRecordStore` instance so the DI `memoryStore` slot and the legacy `qdrantService` singleton share state. Dependency direction is strictly inward: callers depend on the port interfaces; the `lancedb/` package depends on them plus `../types.js`; no port file imports a backend client library.
