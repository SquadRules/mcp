Layered around a single `MemoryQdrantStore` facade (`store.ts`) that owns the `QdrantClient`, resolves collection aliases, and delegates to three internal collaborators:
- `store-methods.ts` — read/search path: Redis-cached retrieval, hybrid query (dense primary + title + activation-pattern vectors plus two BM25 legs fused via RRF), score boosting over payload fields, and space/tenant filtering.
- `store-adapter.ts` — write path: parses Markdown into header-based or default adapter memories via `adapter-builder.ts`, dispatches to `store-adapter-header-handler.ts` / `store-adapter-default-handler.ts`, runs similarity checks, and persists through `store-artifact.ts`.
- `store-init.ts` — bootstrap/migration: detects existing layout, migrates from legacy single-vector to named vectors, recreates collections for BM25 sparse-vector support, creates full-text payload indexes, and backfills activation-search vectors.

Cross-cutting concerns are split into focused files: `adapter-contract-blocks.ts` and `validate-protocol-structure.ts` parse/validate the ```json contract blocks and required H1/H2 sections; `activation-search-backfill.ts` and `activation-search-fields.ts` manage activation-pattern vectors; `qdrant-point-to-memory.ts` maps Qdrant points to the `Memory` type; `memory-accessors.ts` and `artifact-metadata.ts` provide payload helpers; `validate-adapter-markdown-size.ts` enforces size limits. Dependency direction is one-way: store → methods/adapter/init → shared qdrant-utils/embedding services; nothing in this module imports callers, keeping it a pure persistence service.
