Layered around three internal boundaries:
- Connection layer (`connection.ts`): `QdrantConnection` wraps the `@qdrant/js-client-rest` client, handles TLS/CA cert loading, health checks, and exponential-backoff reconnection via `executeWithReconnect`, which is the single entry point every operation uses.
- Domain modules (one file per concern): `initialization.ts` (collection creation, payload indexes, aliasing, backfill), `memory-store.ts` / `memory-retrieval.ts` / `memory-updates.ts` (CRUD on memory points), `search.ts` (vector search), `protocol.ts` (protocol step queries), `quality.ts`, `resources.ts`, `listing.ts`, `reward-propagation.ts`, `snapshots.ts`. Each module receives a `QdrantConnection` instance and delegates all I/O to it — no direct client access outside this module.
- Facade + singleton (`service.ts` + `index.ts`): `QdrantService` exposes a stable public API delegating to the domain modules; `qdrantService` is a runtime-selected singleton that resolves to either `new QdrantService()` or the shared embedded record store (`../vector-store/embedded-store-singleton`) when Qdrant is not configured, so callers import from `services/qdrant` without branching.
Dependency direction: service.ts → domain modules → connection.ts → `@qdrant/js-client-rest`; configuration flows in from `../../config.js` and `../embedding/config.js`.
